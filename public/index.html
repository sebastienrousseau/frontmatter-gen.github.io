Engine Architecture

Engineered for predictable latency and untrusted input safety.

Every module in frontmatter-gen separates zero-copy borrowing from heap allocation so callers pay only for the work they request.

01

Zero-Copy Fence Splitting

extractor::extract_raw_frontmatter locates YAML (---), TOML (+++), or JSON ({ ... }) boundaries in a single forward scan and returns borrowed (&str, &str) slices with zero heap allocation.

02

YAML 1.2, TOML 1.1 & JSON

Powered by pure-Rust noyalib (YAML 1.2 with explicit Value::Tagged preservation and no Norway boolean coercion), toml 1.1, and serde_json, unified behind a single recursive Frontmatter model.

03

HTML Meta & Template Engine

meta::generate_metatags transforms frontmatter maps into entity-escaped HTML <meta>, Open Graph (og:*), and Twitter Card tags, while the optional ssg feature drives static site builds.

Frequently Asked Questions

Why does frontmatter-gen use noyalib instead of serde_yaml?

serde_yaml was archived upstream in March 2024 and implements YAML 1.1, where unquoted scalars like no or off coerce to booleans. frontmatter-gen uses noyalib, an actively maintained, pure-Rust YAML 1.2 parser with zero unsafe code and explicit tag support.

Does extract_raw_frontmatter allocate on the heap?

No. extractor::extract_raw_frontmatter returns Result<(&str, &str), ParseError> borrowed directly from your input &str. You only allocate when you parse the raw slice into a Frontmatter map.

How do I protect my server against deeply nested frontmatter payloads?

Use parser::parse_with_options with a ParseOptions struct setting max_depth (for example, Some(16)) and max_keys (for example, Some(128)). Payloads exceeding either threshold return ParseError::InvalidFrontmatter immediately.

Are the CLI and SSG engine mandatory dependencies?

No. The default build includes only the core extractor, YAML/TOML/JSON parsers, and HTML meta tag generator. The cli feature (fmg binary) and ssg feature (static site engine) are strictly opt-in.
